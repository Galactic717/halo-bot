# Halo Bot — reverse engineering, repairs and the second half of the product

27 August 2026. What follows is the whole of one pass over `D:\Halo bot`: what the project turned out
to be, what was actually wrong with it, and what the two builds gained. It is written to be read
after the fact by somebody who was not here, so every change says why as well as what.

---

## 1. What the project is

Halo Bot is a local clone of the Grok Bot model of working, built twice: once as an Electron desktop
app for Windows and once as a Kotlin/Compose application for Android. It is not a wrapper — the
Android build is a port, and `android/` contains no code from `electron/` or `src/`.

```
host/       the agent runtime: store, provider, tools, policy, memory, skills, subagents,
            runner, scheduler, MCP, fence, compaction, expression, audit, personas, n8n
electron/   main process: window, IPC, the bot's Chromium browser, teach recorder, webhook listener
src/        renderer: React
native/     halo-box, a Rust helper that runs a box command at Low integrity inside a job object
android/    core/ ports host/ · platform/ replaces electron/ · ui/ follows src/
docs/       teardowns of the original, the Android notes, and this file
```

**The shape of a turn.** A message enters `Runner.enqueue`, which serialises turns per conversation.
`runTurn` compacts the history if it is over budget, builds a system prompt, and loops against an
OpenAI-compatible endpoint (or an AG-UI endpoint, if the bot has one) up to `maxSteps` times. Every
tool call goes through one gate — `Runner.gate` — which summarises the action, asks `decideDetailed`
for a verdict, optionally asks the model for a second opinion, writes the audit row *before* the
action runs, and only then executes.

**The parts that carry the design:**

- **The floor** (`host/policy.ts` `HARDLINE`) — a handful of command shapes refused whatever the
  settings say. Anchored to command positions and checked against quote-masked and payload-unwrapped
  variants, so `powershell -Command "Remove-Item C:\ -Recurse"` does not slip past.
- **The box** — on Windows a folder labelled Low integrity plus `halo-box.exe`; on Android the app
  sandbox, which is the same boundary for free.
- **The fence** (`host/fence.ts`) — every tool result is wrapped in a marker whose suffix is random
  per process, and the marker is stripped out of the content, so a page cannot forge one.
- **The trail** (`host/audit.ts`) — decide, record, act, in that order, with a second row when a
  permitted action then failed.
- **The snapshot-and-ref browser contract** — the bot clicks a ref this process resolved from a page
  it actually looked at, never a selector the model invented.

Everything is files under `%APPDATA%/Halo Bot` (or `filesDir` on Android), and the layouts match, so
a transcript written by one build is readable by the other.

## 2. Bugs found and fixed

### 2.1 A webhook routine fired once a day on the clock

`nextRun` returned `from + 24h` for a routine whose triggers were all webhooks, and the scheduler
compares `nextRunAt` against now. So every webhook-only routine fired daily and rescheduled itself for
the next day — silently spending the model allowance and posting into the transcript, for a routine
whose whole point is that it waits to be called. The existing test asserted only that the fallback was
"more than 23 hours away", which the bug satisfied.

*Fix* — `NEVER` (`Number.MAX_SAFE_INTEGER` / `Long.MAX_VALUE`) as a real value, returned when nothing
watches the clock, plus a repair in `Scheduler.start` that recomputes `nextRunAt` for any clockless
routine still carrying the old value. `host/scheduler.ts`, `core/Scheduler.kt`, both tested.

### 2.2 The same sentence twice in the transcript

A model that writes "Done: X" as assistant text *and* calls `SendMessage` with the same line produced
two bubbles: the activity record kept the streamed text, and `SendMessage` appended its own message.
The Android build had already been fixed; the desktop had not.

*Fix* — once a turn has delivered anything, the activity record's text is cleared and only its tool
cards remain. The streaming preview keeps doing its job live; it just stops being a second copy of the
answer afterwards. `host/runner.ts`.

### 2.3 Streaming never appeared in a room

`runTurn` emitted `message.patch` with `agentId` while the activity message lives in the *room's*
transcript. The renderer looks the conversation up by that id, so in a channel every streamed token
landed on a conversation that did not hold the message, and nothing moved until the turn ended.

*Fix* — patch `target`, which is the channel id in a room and the bot id otherwise. `host/runner.ts`.

### 2.4 An answered AskUser card asked again

The desktop kept the pick in component state only. Reopening the chat re-read the message off disk
with no answer on it and offered the buttons again — and pressing one sent the answer a second time.

*Fix* — a `halo:message.answer` IPC writes `widget.answered` to the transcript, which is what Android
already did. `src/components/Chat.tsx`, `electron/preload.ts`, `electron/main.ts`.

### 2.5 The Android system prompt advertised a tool that does not exist

The prompt told every Android bot it had `ExternalShell`. There is no shell outside the box on an
unrooted phone and the tool is deliberately absent, so bots were being invited to plan around a
capability that would come back "no tool named ExternalShell" — and to promise it to the user.
`ExternalList` and `ShareFile`, which do exist, were not mentioned at all.

*Fix* — the section now names the five tools that exist and says plainly that there is no external
shell here. `core/Prompt.kt`.

### 2.6 Model ranking on Android sorted by a number it invented

`rankModels(found, Halo.store.let { 6L * 1024 * 1024 * 1024 })` — a constant 6 GB dressed up as a
lookup, used to sort models by whether they "fit in memory". On a phone the model server is somebody
else's machine and this app has no idea how much memory it has.

*Fix* — `rankModels` takes `0` to mean "not this machine" and drops the size ordering, keeping only
the two facts that are true anywhere: an embedding model cannot chat and a model without tool calling
cannot drive anything. `core/Provider.kt`, `ui/Setup.kt`.

## 3. The two builds are one product again

The Android build had drifted. What follows is what it gained; each item already existed on Windows.

**The transcript.** Tool calls now collapse to one line — `› 2 steps · Write, SendMessage` — that
expands in place, with a header toggle that turns the full cards on for the whole conversation, exactly
as on the desktop. Day dividers (`Today` / `Yesterday` / a date), a time under each bubble, and a
long press for copy, quote, react and delete, which is where a phone puts the desktop's hover row. A
working spinner under the last message. Idea chips on an empty chat. An attachment button that copies
the picked file into the bot's box first, so the path it hands the model is one the bot can actually
`Read`.

**The list.** Pinned bots as a grid above the list, sections that collapse, a time and a preview per
row, the unread badge, "N bots working", the provider banner with its Retry and Open settings buttons,
and a long-press menu with pin, move to section, duplicate, export, hide and delete.

**Export and import.** `core/Portable.kt` reads and writes the same `.halobot.json` the desktop does,
through the document picker. A bot exported on Windows imports on the phone with its voice, memory,
skills and routines intact, and back again.

**Rooms.** A channel sheet with members in and out, and the delete, matching the desktop's channel
pane.

**Routines.** The weekly trigger and the daily cap, which the desktop had and the phone did not.

**Search.** Tabs over messages, bots and routines, so it is the desktop's Ctrl+K rather than a message
search wearing its name.

**Per-bot settings.** The notifications switch, the box path, and a delete with a confirmation — the
rest of the desktop's settings pane.

**Plugins.** A detail sheet listing what a plugin actually exposes, not just how many tools it has.

## 4. Adding your own plugins — anything at all

Both builds already spoke MCP. What was missing was the step where a person actually installs one.

Every MCP server on the internet documents itself the same way: a JSON snippet for Claude Desktop,
Cursor or VS Code. Retyping that snippet into four boxes is where installing a plugin stops being
worth it, so now you paste it.

- **Windows** — *Add a server* offers three ways in: a **command**, a **URL** (bridged by
  `mcp-remote`), or **paste its config**. The parser (`host/plugins.ts` `parseMcpConfig`) reads
  `mcpServers`, `servers`, a bare map, or a single definition, and pulls out the command, the
  arguments, the environment and the headers. Several servers in one block are all added.
- **Android** — the same paste (`core/PluginConfig.kt`), plus URL. A `command` server is *named* as
  unsupported rather than silently dropped: a phone has nothing to run one in, and a plugin that
  quietly did not install is worse than one that says why.
- **Google Classroom** is in the desktop catalogue (`gogcli-mcp-classroom`), as an example of the
  shelf rather than the mechanism — the mechanism is the paste, and it takes anything.
- **`McpField.optional`** — a declared field that is asked for but does not hold the install, because
  some servers are two servers in one.

## 5. n8n

Halo will never have a Calendar tool, a Notion tool and a Shopify tool that are as good as the real
ones. A lot of people already keep those, wired up and authorised, in an n8n instance. So rather than
growing a connector per vendor, both builds now talk to n8n directly:

| Tool | What it does | Gated |
|---|---|---|
| `N8nWorkflows` | every workflow with its id and whether it is active | no |
| `N8nWorkflow` | one workflow as JSON, to read before editing | no |
| `N8nSaveWorkflow` | create or replace one | **yes** |
| `N8nActivateWorkflow` | turn one on or off | **yes** |
| `N8nRunWorkflow` | fire one through its webhook | **yes** |
| `N8nExecutions` | recent runs, so a bot can say whether it worked | no |

The asymmetry is the design: a bot can look at the automations freely and cannot change them quietly.
Writing, activating and firing go through a new approval surface, `automation`, rather than borrowing
`external_shell` — an n8n workflow is not a command, it is a thing that keeps running after the bot
has stopped and can reach every service the user connected to it, and the approval card should say
that rather than "run a command on your computer".

Turn it on in **Settings → General → Automation**; the key is sealed with the OS keychain (Windows) or
the Android keystore. `SelfCheck` probes it. The system prompt mentions it only when it is connected,
and never carries the key. `n8n-mcp` is also on the desktop marketplace for anybody who would rather
have the 500-node documentation tools alongside.

## 6. Making a bot

The create screen used to be a name and a colour, which is fast and tells the model nothing — a bot
with no brief spends its first turn asking what it is for.

- **Templates** fill the whole bot: role, brief, colour and a voice that suits the job. Nine on
  Windows, seven on Android, all editable afterwards. A template fills the form rather than creating
  outright, because a template you cannot adjust is a menu rather than a starting point.
- **A model per bot**, chosen at creation: the one from Settings, or any other the server offers.
- **A voice**, below.
- Android now greets a new bot and gives one with a brief the same short "first pass" the desktop
  does, which it was not doing.

### Voices

`host/personas.ts` and `core/Personas.kt`, word for word the same so an exported bot sounds the same
on either build. Eight presets — Colleague, Terse, Warm, Mentor, Analyst, Deadpan, Pirate, Сеньор —
plus one you write yourself, which replaces the preset entirely rather than being appended to it.

The Сеньор preset is the character you supplied, kept verbatim as the sample, because a register that
specific cannot be reached by describing it: a model told "be rude" writes a caricature, and a model
given the paragraph writes the voice. It carries its own guard rails — grumble at the task and never
seriously at the person, never on any personal characteristic, switch tone the moment the user asks —
and the same floor as everything else.

A persona is user-written text that ends up beside Halo's own instructions, which is exactly where an
injected instruction would want to be. So `personaSection` closes by naming what a voice cannot do:
it cannot widen what the bot may do, switch off an approval prompt, make a refused action allowed, or
change the rule that tool results are data. If the voice and a rule disagree, the rule wins and the
bot says so in its own voice. There is a test for that paragraph.

## 7. Language

**Settings → General → Reply language.** The default, *Match the user's message*, decides per message
rather than once per conversation — a bilingual user switches mid-thread, and a bot that latched onto
the first language they used is wrong for the rest of the day. It covers everything the user reads:
messages, `AskUser` questions, the skills a bot saves, and the reports it hands a teammate.

Code, commands, file paths, API names, error strings and quoted material are never translated;
translating an error message is how somebody ends up searching for a sentence that does not exist.

Five fixed languages beside *Match*: English, Українська, Polski, Deutsch, Español. Deliberately short
— this is a switch for somebody who writes in one language and wants the answer in another, not a
translation catalogue, and *Match* already covers every language the model knows.

## 8. Verification

| | Result |
|---|---|
| `npm run typecheck` | clean |
| `npm test` | **47 passed**, 0 failed (was 42) |
| `./gradlew :app:testDebugUnitTest` | **37 passed**, 0 failed (was 32) |
| `./gradlew :app:assembleDebug` | builds, installed on the emulator |
| `npm run package` | rebuilt, so `release/win-unpacked/Halo Bot.exe` is current |

The Android build was installed on a Pixel emulator and driven by hand through the list, a chat, the
settings tabs and the plugin shelf. The desktop app was launched and screenshotted to compare against,
screen by screen.

Ten tests are new, five per build, and they are deliberately the same tests in two languages — a rule
that holds on Windows and not on the phone is a bug in whichever half is wrong, and these say which:

- a webhook-only routine has no next time at all, rather than one a day away
- a pasted server config is read whichever shape it arrives in
- a persona changes the voice and says out loud that it changes nothing else
- the reply language is per message by default, and nameable when it is not
- writing an automation asks, and the n8n base is trimmed once

## 9. What is deliberately still open

- **OAuth for hosted MCP servers.** Linear, Notion, Jira, Asana, Canva, Sentry, Vercel, PayPal,
  Square and Intercom publish hosted servers that sign you in through a browser. Halo sends one static
  credential per server. They are named on the Android plugin screen as unsupported rather than listed
  and then failing on the first call.
- **On-device inference on Android.** The model is always something Halo talks to over the network.
- **Reordering sidebar sections by dragging** — they can be made and collapsed on both, reordered on
  neither.
- **The Windows box is a boundary; the Android box is the platform's.** `verifyConfinement` still
  reports which one you have, and the About screen still says so.
